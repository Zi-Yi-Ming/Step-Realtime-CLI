# step-cli 基线实测评估报告（2026-08-30）

> 目的：在动手优化前，用真实任务实测当前 fork 的缓存命中率与指令遵循/工具调用质量基线，用数据决定优化优先级。
> 方法：本地记录代理（`scripts/eval/llm-proxy.mjs`）透明接管 `STEP_BASE_URL` 流量，逐请求落盘；5 类任务 × 多轮运行；原始数据在 `evals/baseline-2026-08-30/`（untracked）。

## TL;DR

1. **缓存侧好消息**：Step Plan API 在 `usage.prompt_tokens_details.cached_tokens` 上报缓存命中，可量化。本次 392 次请求 / 1590 万 prompt tokens，**整体命中率 94.8%**。系统 prompt 每请求字节稳定。缓存优化不是当前瓶颈。
2. **两个意外发现**：StepFun 的缓存**不是严格前缀制**（index 1 的动态块每轮重写，命中率仍 97%+）；命中率与**请求节奏强耦合**（连续快速请求时 50-58%，慢速时 94-97%）——缓存写入是异步的，追不上高速 agent 循环。这可能是"Claude Code 用 Step 模型命中率 <50%"的真正原因。
3. **Guardrails 侧坏消息**：14 次运行 8 成功、**2 次失控循环**（一次 600 秒 305 个请求烧掉约 1480 万 tokens、一次 90 秒超时）、2 次被自建熔断拦截、1 次任务静默未完成。失败模式高度一致、可修复，**guardrails 是明确的优先方向**。
4. **A/B 归因**：上游英文 prompt 同任务集成功 2/7，fork 中文 prompt 成功 5/7——失败模式为上游固有，中文 prompt 改进有效，应保留。

## 实验设置

- 模型 `step-3.7-flash`，endpoint `https://api.stepfun.com/step_plan/v1/chat/completions`（经本地代理）
- 保护措施：runner 单次运行 90s 超时 + 代理 30 次/分钟熔断（429）——两者都被验证有效，CLI 对 429 干净重试 3 次后退出
- 任务集：T1 只读总结（×2+resume）、T2 定位检索（×1+resume）、T3 精确编辑（×2）、T4a 调用不存在工具（×2）、T4b 读取不存在文件（×2）、T5 plan 模式 code review（×2）

## 缓存发现

### 1. 指标可测性（探测脚本 3 连发同前缀请求）

| 请求 | cached_tokens | prompt_tokens | 延迟 |
|---|---|---|---|
| #1 冷 | 0 | 5427 | 1140ms |
| #2 紧跟 | **0** | 5427 | 1124ms |
| #3 | **5312 (97.9%)** | 5427 | **601ms** |

结论：缓存真实存在、可测量，且**写入异步有延迟**——紧跟的第二次请求都未命中。

### 2. 上下文结构（对相邻请求做逐消息哈希对比）

- 系统 prompt（index 0）：316/321 请求哈希一致，字节稳定 ✅
- **index 1 是 `<context-decisions>` 决策轨迹块**（assistant 角色），每轮被重写增长（304c→383c→442c→…），64/320 相邻对在此分歧
- 其余历史纯追加（divergence@30+，256 对）

### 3. 非严格前缀缓存的证据

若为严格前缀缓存，index 1 每轮重写应导致其后全部 miss（run2 后期 prompt 94K tokens 只可能命中 ~7K）。实测 run2 循环期间 `cached=94016/94413 (99.6%)`。**StepFun 缓存按块/分段工作，容忍中间块变更**——"把动态块移到尾部"的传统优化对本端点收益存疑，动手前需先做 A/B 验证。

### 4. 命中率与请求节奏耦合（重要）

| 场景 | 请求间隔 | 命中率 |
|---|---|---|
| T1-run1 错误循环（~1.4s/请求） | 快 | 58.6% |
| T2-run1 错误循环（~1.5s/请求） | 快 | 50.7% |
| T1-run2 失控循环（后期 2-5s/请求） | 中 | 97.4% |
| T4b/T5 少量慢速请求 | 慢 | 72-96% |

与探测 #2 未命中互证：**新前缀的缓存写入需要时间生效，高速连续请求系统性 miss 增量部分**。对 agent 场景意味着：跑得越快、轮次越多，增量 token 越贵。这是"Claude Code + Step 模型 <50%"的一个可解释假设（Claude Code 请求节奏快），也是后续可做实验验证的方向（如在客户端做最小请求间隔或重试）。

### 5. 其他

- 触发上下文压缩时会发出独立 system prompt 的压缩请求（"CONTEXT CHECKPOINT COMPACTION"），计费与主对话分开
- 工具数组顺序字节稳定 ✅（对任何前缀缓存都友好）

## 指令遵循 / 工具调用失败模式

### FM1：幻觉 Claude Code 风格的顶层工具名（最高频）

T1、T2 的第一反应都是调用顶层 `read_file`——**该工具不存在**（Code Mode 面貌下顶层只有 `exec`+`wait`）。收到 `UNKNOWN_TOOL` 错误后模型倾向原样重试：

- T1-run1：连续 13 轮 UNKNOWN_TOOL 后才改用 `exec` 自救成功
- T2-run1：90 秒全程 read_file 循环，未能自救，超时被杀

`UNKNOWN_TOOL` 错误信息只说 "Tool 'read_file' is not registered"，**不附带可用工具清单**——模型没有自我修正所需的信息。

### FM2：参数微变逃逸重复检测 → 无限循环

T1-run2（灾难现场，600s/305 请求/1480 万 prompt tokens）：模型在 exec 沙盒里调 `run_command`，失败后**误诊为超时问题**，开始指数级抬高 `timeout_ms`（2×10^10 → 2.4×10^37 → 3.6×10^76…）。每次只变一个参数，完美绕过 `REPEATED_TOOL_CALL` 指纹拦截（指纹含完整参数）。

### FM3：exec 沙盒反馈歧义 → 模型误诊

沙盒返回体形如 `ok: true` + 内容里嵌 `✗ run_command ...` + 模糊的 `Diagnostic: Script completed without a returned result`。模型无法区分三种完全不同的问题：脚本没返回值 / 工具执行失败 / 命令超时。FM2 的误诊直接源于此。Windows 下 shell 命令兼容性（`cat`/`ls`）可能进一步放大混乱。

### FM4：幻觉"可用工具列表"

T4a 中模型对不存在工具的处理本身正确（拒绝+给替代方案 ✅），但它**报出的可用工具清单是编的**（声称有 `run_command`、`read_file` 等）——模型对工具面貌没有可靠认知。

### Code Mode 设计与模型认知的错位

Code Mode 把所有工具折叠为顶层 `exec`+`wait`，真实能力以 `tools.*` 绑定清单写在 exec 的 description 里（apply_patch / edit_file / read_file / run_command / find_tools / skills / task / teammate / update_plan 等）。设计意图是降低弱模型工具调用负担，但 step-3.7-flash 的先验是"顶层多工具"（Claude Code 风格），两者错位产生了 FM1/FM4。T3 中模型还在沙盒里发明 API（`tools.write_file` 不存在）、给 `edit_file` 传空 `search`、乱派子代理，30 次调用后文件仍未创建。

## 优化优先级建议

### P0：工具调用 guardrails（数据支撑最硬）

1. **`UNKNOWN_TOOL` 错误信息附带可用工具清单**（或 top-5 相似名建议 + `find_tools` 提示）。改动点：`packages/core/src/tools/runtime.ts` `unknownToolResult()`。成本极低，直接针对 FM1/FM4 的信息缺失。
2. **近似重复调用检测**：指纹计算对数值参数做归一化（或对"同工具+同路径+仅数值不同"降敏感），连续同工具失败 N 次后注入强制换策略提示或终止。针对 FM2。
3. **exec 沙盒反馈结构化**：把 `✗` 事件带上 `error.code`，明确区分 `SCRIPT_NO_RETURN` / `TOOL_FAILED` / `TIMEOUT`；`ok:true` 里嵌失败行的格式改为逐事件结构。针对 FM3。
4. **prompt 补丁**：默认 system prompt 明确"顶层工具面貌以本会话工具表为准，不要假设其他产品（如 Claude Code）的工具名；exec 沙盒内可用绑定以 exec 描述为准"。针对 FM1/FM4 的认知错位。

### P1：缓存（收益有限，先验证再动手）

- 结构已达标（system 稳定、工具序稳定），整体 94.8%。
- 唯一值得做的实验：**节奏-命中率耦合**。在客户端对连续 LLM 请求做 ~2s 最小间隔或对 miss 的增量部分做低成本重试，量化收益后再决定是否保留。`<context-decisions>` 移尾部方案仅建议在 A/B 验证块级缓存行为后再做。

### P2：可观测性

- 把 `UNKNOWN_TOOL` / `TOOL_EXECUTION_FAILED` / 近似重复 / 熔断触发等事件聚合计数进 `AgentRunResult`，让下一轮优化有直接的数字对照（本次报告的数据是靠代理日志离线还原的）。

## P0-②③ 修复记录（2026-08-31）：指纹归一化 + exec 反馈结构化

### P0-② 数值微调逃逸封堵（`231692c`，`packages/core/src/agent/tool-fingerprint.ts`）

- 指纹归一化把 |数值| > 1e9 的参数折叠为 `__HUGE_NUMBER__` 占位：FM2 的指数级 timeout 爆炸（2e10 → 2.4e37 → 3.6e76）全部落进同一指纹，被既有 `repeatedToolCallLimit` 正常拦截；合法参数（timeout/offset/limit ≤ 1e9）不受影响
- 拦截报错明确告知"只改数值参数也会被抑制"，直接矫正"误诊为超时→抬参数"的回路
- 指纹逻辑从 agent-loop.ts 迁至独立模块，补 8 个单测

### P0-③ exec 沙盒反馈结构化（`35987cb`，`packages/core/src/tools/code-mode/service.ts`）

- ✗ 行追加失败调用的真实 `summary`（此前被丢弃——错误码/stderr 只留在数据里不进模型上下文）
- completed summary 如实计数：`Script completed · 2 tool calls, 1 failed tool call`
- 无返回值 Diagnostic 在有失败时明确排除超时误诊方向（"tool-level failures, not timeouts"）
- `data.failedToolCalls` 结构化计数；`renderCellResult` 导出并补 6 个单测

### 端到端验证（`evals/p0verify-2026-08-30/`，34 请求 / 约 44 万 tokens）

- **T2 定位检索**：47s exit 0，20 次调用零无效重试，output 质量好（准确定位 `createToolCallFingerprint` 并解释三部分机制）。缓存 49.4% 属快节奏正常区间
- **T3 精确编辑**（基线两次熔断失败）：29s、9 次调用。恢复链教科书级：`import` 报错 → 改 `require` → 又报错 → 转向嵌套工具 → 写操作被权限 gate 后以 Exec-plan 请求确认收尾。零重复调用、两次脚本失败均正确归因。文件未创建是权限确认机制的正确行为（`--json` headless 模式下写操作 gate 生效），不再是基线的乱试循环
